# Code of Conduct

Beech CMS is an open project and everyone who participates in it — by writing code, opening issues, reviewing pull requests, or joining discussions — is expected to follow this code of conduct.

---

## Our Commitment

We are committed to maintaining a welcoming, respectful, and collaborative environment for everyone, regardless of experience level, background, or identity. We believe good software is built by people who treat each other well.

---

## Expected Behaviour

- **Be respectful.** Disagreements happen. Discuss ideas, not people. Critique code and decisions directly, without attacking the person behind them.
- **Be constructive.** Feedback should help the recipient improve. If something is wrong, explain why and suggest a better path.
- **Be patient.** Not everyone has the same context, experience, or time. Give people the benefit of the doubt.
- **Be honest.** If you do not understand something, say so. If you made a mistake, own it. Clarity is more valuable than appearing infallible.
- **Stay on topic.** Keep discussions focused on the project. Off-topic conversations belong elsewhere.

---

## Unacceptable Behaviour

- Personal attacks, insults, or derogatory comments of any kind
- Harassment, threats, or intimidation — public or private
- Dismissing contributions without explanation
- Deliberately submitting low-quality work that wastes reviewers' time
- Sharing others' private information without explicit consent

---

## Standards for Technical Collaboration

Beyond general conduct, contributors are expected to engage with the codebase responsibly:

- **Read before you write.** Understand the existing architecture — documented in [`docs/vertical-slice.md`](docs/vertical-slice.md) and [`docs/architecture.md`](docs/architecture.md) — before making structural changes.
- **Ask before refactoring.** Large architectural changes should be discussed in an issue before implementation begins.
- **Do not submit incomplete work as finished.** A pull request that leaves half-resolved logic, open `TODO` comments without issue references, or broken tests wastes everyone's time.
- **Review seriously.** If you approve a pull request, you share responsibility for what it introduces. A rubber-stamp approval is not a review.
- **Respect the branching strategy.** All work goes to `devs`. The `master` branch is managed exclusively by the project owner and reflects published npm releases. Direct pushes to `master` are not acceptable.

---

## Enforcement

Violations of this code of conduct may result in contributions being rejected, discussions being closed, or — in serious or repeated cases — access to the repository being revoked.

If you witness or experience behaviour that violates this code, open a private issue or contact the project owner directly.

---

## Scope

This code of conduct applies to all spaces managed by this project: the GitHub repository, issues, pull requests, discussions, and any other channels where project work takes place.
