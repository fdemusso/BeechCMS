# ROADMAP — BeechPal (Command Palette as the keyboard-first navigation and action surface)

Feature brief: `stages/00_ideation/output/feature_brief.md`

The brief does not fit one sprint. It spans the dashboard palette engine, two dashboard-only local
tool families, a search API contract change, a cross-slice declaration contract for context actions,
and a new server-side per-user container (core + migration + API) whose dashboard consumer must land
after it. Detailed Task Details exist ONLY for the sprint currently in flight.

## Ordering rationale

- **Engine first.** Every later sprint adds a provider. Without the contract, each one would
  extend the hand-written `RootView` and the RBAC projection would be re-done per row.
- **Local tools before search.** The coexistence rule (brief rule 9) needs per-item scores and the
  prefix router; both are cheaper to prove on synchronous providers before the async lane exists.
- **API before UI, per server change (3 → 4, 8 → 9).** Search metadata and the UI preferences
  container are server contracts that the dashboard projects; each is validated alone, as in the
  previous multi-sprint features.
- **Context actions after the engine, independent of search.** They need only the provider contract
  plus a shared declaration contract, so they can run in parallel with 2–5 if needed.
- **Row actions apart from search (4 → 4b).** The submenu is an engine capability with its own
  keyboard bindings; validating it separately keeps the async lane's review focused. Search rows
  are its first consumer (copy ID), so it follows entry 4.
- **Pins last.** They depend on the stable id convention (sprint 1), the row submenu (sprint 4b) and
  the server container (sprint 8).
