# ROADMAP — RBAC-Native Dashboard (role-targeted tabs, scope-filtered widgets, legacy role removal)

Feature brief: `stages/00_ideation/output/feature_brief.md`

The brief does not fit one sprint. It names six phases that merge sequentially (§4 "Vincoli di
consegna"): the data-route closure must ship alone and first; the layout contract must exist in
`@beechcms/core` + `apps/api` before the dashboard can render or edit it; `manage_layout` needs a
D1 migration before its enforcement; the `users.role` removal touches platform security beyond the
dashboard and is planned apart. Detailed Task Details exist ONLY for the sprint currently in flight.

## Ordering rationale

- **Data closure first and alone (brief §4).** It is the only phase that fixes a violation live
  today, and it must be releasable even if every later sprint slips. It changes no layout or
  dashboard contract, so nothing downstream blocks it.
- **API before UI, per phase.** Phases 2 and 4 each change a server contract (layout shape,
  save enforcement) that the dashboard then projects. Shipping both in one PR would leave the
  server contract unvalidated on its own, which is the split criterion in the stage contract.
- **`requires` before `manage_layout`.** The locked-widget decision in sprint 5 ("can this author
  use this widget?") is exactly the `requires` evaluation sprint 4 introduces; doing it the other
  way round would invent a second authorization path.
- **`manage_seeds` before legacy removal.** `requireAdmin` and the `legacy-admin` route kind can
  only be deleted once `/api/seeds/*` has an RBAC gate.
- **Readers before storage (entries 8 → 9).** Sprint 8 replaces every gate that reads the legacy
  axis, a security-relevant behaviour change reviewed on its own. Sprint 9 then deletes the column,
  the claim and the types with the compiler as the oracle; folding both into one diff would bury
  four authorization changes in ~40 mechanical test-fixture edits.
- **Interim layout write gate.** Between sprints 2 and 5 the layout write gate is
  `manage_roles@*` (the structural permission per brief rule 15). Sprint 5 widens it to
  `manage_layout` for content-only edits.
