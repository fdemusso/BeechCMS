SECTION 1 — WHY THIS SPRINT EXISTS FIRST
==========================================================================

After sprints 01 and 02, a project scaffolded with 0.10.x is broken in two ways:

- **Its Public API is dead.** `wrangler.jsonc` `vars` still holds `PUBLIC_READ_API_KEY` / `PUBLIC_WRITE_API_KEY`,
  which the runtime no longer reads. So every keyed request answers 403 `public-api-not-configured`, and the error
  message already points to `npx beech keys:migrate`, which does not exist yet.
- **Its secrets are still public.** `JWT_SECRET` and `PUBLIC_TIME_TRAP_SECRET` sit in a committed file and in its git
  history (#995).

The ROADMAP forbids releasing `api`, `client` and `cms` until this command exists. Sprint 04 (docs and changelog)
cites it, so it must exist first. The target layout is the one sprint 02 fixed for fresh scaffolds:

- `vars` = `ENV`, `CORS_ORIGINS`, `BEECH_PUBLISHABLE_KEY`, `APP_URL`;
- `.dev.vars` = `JWT_SECRET`, `BEECH_SECRET_KEY`, `PUBLIC_TIME_TRAP_SECRET`, `PRIVACY_MASTER_KEY` (+ R2).

After migrating, a 0.10.x project is indistinguishable from a fresh scaffold on these keys, except for user edits,
which are preserved.

VSA and Botanical Engine: no runtime code changes. The command lives in `packages/cli`, outside the slices, and
touches no database.

### T1 — `lib/key-model.ts` and `findTopLevelObjectSpan`

Why: `init` (warning) and `keys:migrate` (removal) must agree on which names are legacy. Locating `vars` in the raw
text needs the string- and comment-aware lexer that already lives in `lib/wrangler.ts`.

New `packages/cli/src/lib/key-model.ts` (MIT header). Verbatim:

```ts
/** Local Public API keys. The same values as the scaffolder (`bin/template.mjs`) and the docs. */
export const DEV_PUBLISHABLE_KEY = 'beech_pk_dev'
export const DEV_SECRET_KEY = 'beech_sk_dev'

/** Key names 0.10.x scaffolds wrote in `wrangler.jsonc` vars; the runtime no longer reads them. */
export const LEGACY_KEY_VARS = ['PUBLIC_READ_API_KEY', 'PUBLIC_WRITE_API_KEY'] as const

/** Secrets 0.10.x committed in `wrangler.jsonc` vars; `keys:migrate` moves them to `.dev.vars` with fresh values. */
export const EXPOSED_SECRET_VARS = ['JWT_SECRET', 'PUBLIC_TIME_TRAP_SECRET'] as const

/** Secrets production must hold after the migration, in the order they are printed. Never `PRIVACY_MASTER_KEY`. */
export const MIGRATED_PRODUCTION_SECRETS = ['JWT_SECRET', 'BEECH_SECRET_KEY', 'PUBLIC_TIME_TRAP_SECRET'] as const

/** Names from LEGACY_KEY_VARS then EXPOSED_SECRET_VARS that are own keys of `vars`, in that order. */
export function legacyVarNames(vars: Record<string, unknown>): string[]
```

Rules for `legacyVarNames`: a name counts when it is an own property, whatever its value (an empty string still
counts, because it is still committed). It ignores every other name, including `BEECH_*` and `PRIVACY_MASTER_KEY`.
It never throws on an empty object.

New export in `lib/wrangler.ts`, placed after `stripJsonc` (verbatim signature):

```ts
/**
 * Offsets of the `{` and its matching `}` for the top-level object member `key` in JSONC text. Strings and
 * comments are skipped, so a `"vars"` inside a value, a comment or a nested object is never matched.
 * Null when the member is absent or its value is not an object.
 */
export function findTopLevelObjectSpan(raw: string, key: string): { open: number; close: number } | null
```

Rules: a single forward scan. It tracks brace and bracket depth, skips string literals with the existing
`stringEnd` (`wrangler.ts:190`) and skips `//` and `/* */` comments exactly as `stripJsonc` does (`L176-180`). A
match is a string token at depth 1 whose unescaped content equals `key`, followed (whitespace and comments allowed)
by `:` and then `{`. `close` is the index of the `}` that brings the depth back. Unterminated input returns null and
never throws.

Tests:

- New `packages/cli/src/test/key-model.test.ts` (vitest unit, pure, MIT header), `describe('legacyVarNames')`:
  - It returns the four legacy names from a 0.10.x `vars` object in constant order, whatever their order in the input.
  - It ignores `BEECH_PUBLISHABLE_KEY`, `BEECH_SECRET_KEY`, `PRIVACY_MASTER_KEY` and unrelated names, and returns
    `[]` for `{}`.
  - It counts a legacy name whose value is an empty string.
- `packages/cli/src/test/wrangler.test.ts` (existing unit suite), new `describe('findTopLevelObjectSpan')`:
  - The span of `vars` in a 0.10.x-shaped config, sliced and parsed through `stripJsonc` + `JSON.parse`, equals
    the `vars` object.
  - A `"vars"` inside a string value, inside a `//` comment and inside `env.production` is not matched: the span
    returned is the top-level one, or null when only those exist (one matrix, a shared shape).
  - It returns null when `vars` is absent, when its value is an array or a string, and for unterminated input.

### T2 — `planKeyMigration`: the pure migration

Why: every decision (what moves, what rotates, what stays, when to refuse) is computed on strings, so it is fully
unit-testable and the command cannot write half a decision. Copy the planner/command split of
`agent-setup.ts:109,130`.

New `packages/cli/src/commands/keys-migrate.ts` (MIT header). Verbatim types and signatures:

```ts
export interface KeyMigrationInput {
  /** Basename of the config file, used in messages: 'wrangler.jsonc' or 'wrangler.json'. */
  configName: string
  /** Content of the config file. */
  wranglerRaw: string
  /** Content of `.dev.vars`. */
  devVarsRaw: string
  /** Returns a fresh secret on every call (production: 32 random bytes, hex). Injected so tests are deterministic. */
  generateSecret: () => string
}

export interface KeyMigrationPlan {
  /** New config content; identical to the input when nothing changes. */
  wranglerRaw: string
  /** New `.dev.vars` content; identical to the input when nothing changes. */
  devVarsRaw: string
  /** Names removed from `vars`, as returned by `legacyVarNames`. */
  removedVars: string[]
  /** `.dev.vars` names that received a fresh generated value, in EXPOSED_SECRET_VARS order. */
  rotated: string[]
  /** Names added with their local value: 'BEECH_PUBLISHABLE_KEY' (vars), then 'BEECH_SECRET_KEY' (.dev.vars). */
  added: string[]
}

/** Computes the migration of a 0.10.x project. Throws CliError when the config cannot be edited safely. */
export function planKeyMigration(input: KeyMigrationInput): KeyMigrationPlan
```

Rules, in evaluation order. Every refusal throws `CliError(message, hint)` before anything is computed for the
output, and the hint states the manual edit.

1. **Parse.** `JSON.parse(stripJsonc(wranglerRaw))`. On failure, refuse: "`<configName>` is not valid JSONC".
2. **`vars` must exist.** The parsed `vars` must be a plain object, and `findTopLevelObjectSpan(wranglerRaw, 'vars')`
   must return a span. Otherwise refuse. Hint: add `"vars": { "BEECH_PUBLISHABLE_KEY": "beech_pk_dev" }` by hand and
   re-run.
3. **Environments.** If any `env.<name>.vars` object holds a name `legacyVarNames` would return, refuse. The message
   lists every `env.<name>.vars.<KEY>` path (names only). Hint: move those values by hand, because the command only
   migrates top-level `vars`. Wrangler does not inherit `vars` into environments, so a silent partial migration would
   leave committed secrets behind.
4. **`.dev.vars` entries.** `parseDevVars(devVarsRaw)` gives `devVars`, and `removed = legacyVarNames(vars)`.
   - For each name in `EXPOSED_SECRET_VARS`: when the name is in `removed`, or `devVars[name]` is missing or blank,
     set it to `generateSecret()` and record it in `rotated`. Otherwise keep the existing value. The value
     committed in `vars` is **never** copied: it is in the git history (brief §4, "Rotazione").
   - `BEECH_SECRET_KEY`: when it is missing or blank in `devVars`, set it to `DEV_SECRET_KEY` and record it in
     `added`. An existing value (for example a custom one) is kept.
   - `PRIVACY_MASTER_KEY` is never read, written, generated or moved, wherever it is (brief rule 7). The same holds
     for every R2 name.
   - If there is at least one entry, the new `.dev.vars` is `upsertDevVars(devVarsRaw, entries)` with the entries in
     the order `JWT_SECRET`, `BEECH_SECRET_KEY`, `PUBLIC_TIME_TRAP_SECRET`, so appended keys match the scaffold
     order. Otherwise it is `devVarsRaw` unchanged.
5. **`vars` edit (text, line-based, only inside the span).**
   - Detect the EOL as `\r\n` if the config contains it, otherwise `\n`. Work on the lines strictly between the line
     of `open` and the line of `close`.
   - Delete the whole line of each member in `removed`. A member line is a line whose first non-blank token is the
     quoted name followed by `:`.
   - When `vars` has no `BEECH_PUBLISHABLE_KEY` own property: if `PUBLIC_READ_API_KEY` was removed, put
     `"BEECH_PUBLISHABLE_KEY": "beech_pk_dev"` at that line's position, with that line's indentation. Otherwise
     insert it as the last member, with the indentation of the previous member line (2 more spaces than the
     `vars` line when `vars` is empty). Record it in `added`. An existing value is kept.
   - Commas: every member line except the last ends with `,`, and the last has none. A trailing `//` comment stays
     after the comma position. Comment-only and blank lines inside `vars` are kept.
   - Every byte outside the edited lines is unchanged.
6. **Postcondition (the safety net).** Re-parse the result with `stripJsonc` + `JSON.parse`. The result must hold all
   three conditions:
   - every top-level member other than `vars` deep-equals the original;
   - `vars` equals the original `vars` minus `removed`, plus `BEECH_PUBLISHABLE_KEY: 'beech_pk_dev'` when it was
     added;
   - `legacyVarNames` of the new `vars` is `[]`.
   On any mismatch, refuse: "`<configName>` vars cannot be edited safely". This covers several members on one line,
   values spanning lines and odd comment placement. Hint: the exact manual edit (remove `<removed>`, add
   `BEECH_PUBLISHABLE_KEY`), then re-run.
7. **Idempotence.** Calling `planKeyMigration` on its own output (same `configName`, any `generateSecret`) returns
   both contents unchanged and three empty arrays, without calling `generateSecret`. It follows from rules 4 and 5.
   The test pins it.

Never throws for any other reason, and never reads the filesystem, the environment or the clock.

### T3 — `keyMigrationReport`, the `keysMigrate` command, wiring

**Report** (pure, same file). Verbatim signature:

```ts
/** Lines to print after a migration. Never contains a value from either file except DEV_PUBLISHABLE_KEY. */
export function keyMigrationReport(plan: KeyMigrationPlan, configName: string): string[]
```

Rules (copy is free, content is fixed):

- **Nothing changed** (all three arrays are empty): exactly one line saying that the project already uses the
  publishable and secret keys, so there is nothing to change. No production block.
- **Otherwise**, in this order:
  - **Local changes.** One line per non-empty group: names removed from `<configName>` vars;
    `BEECH_PUBLISHABLE_KEY = beech_pk_dev` added (read only, safe in the browser); `.dev.vars` names given fresh
    values; `BEECH_SECRET_KEY` set in `.dev.vars` to the local development key (the value is not named, as in
    sprint 02's scaffolder note). Then one line saying that `PRIVACY_MASTER_KEY` was not touched.
  - **History warning**, when `removedVars` is non-empty. The old values are still in the git history: treat them as
    compromised. Only rotation makes them harmless, and this command does not rewrite history. When `JWT_SECRET` is
    in `removedVars`, add one more line: sessions signed with the old secret stop working, so everyone signs in again.
  - **Production block**, headed "run by hand, this command never writes to Cloudflare":
    1. Only when `removedVars` is non-empty: `npm run deploy` comes first. A secret cannot share its name with a
       plain-text var (Cloudflare error 10053), so the deploy must remove the old vars before the secrets can be
       set. Logins and secret-key writes fail until step 2 is done.
    2. One `npx wrangler secret put <NAME>` line for each `MIGRATED_PRODUCTION_SECRETS` entry, iterated from the
       constant.
    3. Use fresh values, never the local ones or the old committed ones. The production secret key starts with
       `beech_sk_live_`. Two generator lines:
       `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and
       `node -e "console.log('beech_sk_live_' + require('crypto').randomBytes(16).toString('hex'))"`.
    4. Never set a new `PRIVACY_MASTER_KEY`: it makes protected fields unreadable.
    5. Clients: browser code sends the publishable key, server code sends the secret key (`@beechcms/client`:
       `publishableKey` / `secretKey`).
